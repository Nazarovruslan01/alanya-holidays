# Правила поддержки Alanya Holidays

Этот документ описывает рабочие границы кода и проверки. Команды установки и запуска —
в [README](../README.md); правила работы агента — в применимых AGENTS.md.
Наличие конфигурации или теста само по себе не подтверждает готовность production.

## Размещение логики

- Контроллеры принимают DTO, применяют guards и передают аутентифицированного
  пользователя в сервис. Бизнес-правила и доступ к данным не переносим в контроллер.
- Сервис отвечает за сценарий: проверки владельца, роли и допустимости операции,
  расчёты и последовательность вызовов. Денежные расчёты используют существующий Money.
- Репозиторий выполняет запросы и RPC через SupabaseService. Атомарность резервирования,
  идемпотентность и конкурентные переходы статусов остаются в SQL-функциях.
  Схему и RLS меняем только версионированными миграциями.
- В модулях с интерфейсными токенами используем одну реализацию через useExisting.
  Не добавляем пустые наследники для совместимости или новый интерфейс без потребителя.
- Сохраняем принятую структуру конкретного модуля: часть модулей имеет каталоги
  application/domain/infrastructure, часть — сервис и репозиторий рядом.
  Изменение одной функции не требует массового перемещения файлов.
- Frontend вызывает backend через api-services и ApiClient. Существующие обращения
  к Supabase Auth, профилю в AuthContext и Storage остаются специализированными путями;
  новую бизнес-логику доступа к БД в UI-компоненты не добавляем.

## Границы products

| Компонент | Ответственность |
|---|---|
| ProductsService | Каталог, товары и варианты, управление товарами продавца и администратора |
| ProductOrdersService | Создание и чтение заказов, доступ покупателя/продавца, доставка, выбор оплаты и статусы |
| ProductDraftsService | Сохранение и публикация черновиков |
| ProductsRepository | Существующие запросы каталога и заказов, вызовы атомарных RPC |
| product-sales-policy.ts | Общая проверка приостановленных gift cards для каталога и новых заказов |

ProductsController направляет операции непосредственно в соответствующий сервис.
ProductOrdersService использует BillingService для создания checkout; webhook и
подтверждение платежа остаются в webhooks. Перенос метода между сервисами не должен
менять порядок проверок, расчёт цены, ключи идемпотентности, DTO или HTTP-ответ.

## Ошибки API

GlobalHttpExceptionFilter возвращает:
`{ success: false, error: { statusCode, code, message, timestamp, path } }`.
Поле message — строка или список строк валидации. ApiClient сохраняет HTTP-статус
и исходное тело в ApiError, извлекает вложенное сообщение и объединяет список
через `; `. Не создаём отдельный разбор этого формата в каждой странице.

Контракт проверяет
[api-error-contract.test.ts](../frontend/tests/api-error-contract.test.ts):
ответ настоящего backend-фильтра передаётся клиенту. При изменении формата обновляем
обе стороны и тест вместе. Внутренние детали непредвиденных ошибок не выдаём клиенту.

## Обязательные проверки

Установка из корня: `pnpm install --frozen-lockfile`.
Сначала запускаем ближайшие тесты затронутого сценария. Для products:

```sh
pnpm --filter @alanya-holidays/backend test --runInBand --testPathPatterns=products
```

Перед передачей backend-изменений:

```sh
pnpm --filter @alanya-holidays/backend test --runInBand
pnpm --filter @alanya-holidays/backend test:e2e --runInBand
pnpm --filter @alanya-holidays/backend exec eslint '{src,apps,libs,test}/**/*.ts'
pnpm type-check
pnpm build
git diff --check
git diff --cached --check
```

Для frontend и контракта API дополнительно:
`pnpm --filter @alanya-holidays/frontend test --run` и
`pnpm --filter @alanya-holidays/frontend lint`.
Для изменения пользовательского потока запускаем соответствующие Playwright-сценарии;
для SQL — применимость миграций и относящиеся к ним проверки БД/RLS из CI.

Backend ESLint также проверяет форматирование Prettier. Скрипт backend lint содержит
--fix; для проверки без изменений используем команду выше. Отдельного formatter-скрипта
у frontend нет. Backend HTTP E2E входят в CI; внешние зависимости в них подменены,
поэтому они не заменяют проверку реальной БД и платёжного провайдера.

Сохраняем существующие проверки при рефакторинге. Регрессионный тест должен воспроизводить
ошибку; количество файлов и тестов само по себе не критерий качества.
В отчёте указываем команды, результаты и пропуски. Коммит, push и deployment —
отдельные действия по намерению пользователя.
